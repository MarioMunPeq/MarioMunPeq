## Dungeon Archive

Compañero de mesa para D&D 5e, pensado para ser rápido y funcionar sin conexión. El SRD completo se genera en tiempo de compilación: **4.024 entidades** (868 hechizos, 1.248 monstruos, 939 objetos mágicos, 777 objetos de equipo, 149 feats, 30 condiciones y 13 acciones) con sus índices de búsqueda y de entidades relacionadas.

El trabajo interesante no está en el CRUD, sino en el pipeline: un importador propio en TypeScript que transforma y **valida** el dataset de 5etools categoría por categoría. El runtime nunca carga el dataset original, solo los JSON ya validados. Alrededor, gestión de personajes, tracker de combate, dados 3D con física real, marcadores de sesión y un tracker de notas.

Lo que más me gusta del proyecto:
- El estado de usuario guarda **IDs canónicos**, nunca copias, con migraciones de esquema entre versiones.
- Firebase Auth y Firestore solo para backup opcional en la nube, cargados con `import()` dinámico: sin variables de entorno la app se distribuye sin nada de código cloud.
- PWA instalable con estrategia de cachés propia, pensada alrededor del peso del worker de física de dados.
- 30 suites de test propias ejecutadas con `tsx`, sin framework de test, y 20 documentos de arquitectura con sus ADR.

## EuroMario

Radar automatizado de noticias de videojuegos con **cero infraestructura**: el repositorio es la base de datos y GitHub Actions es a la vez planificador y despliegue. Diariamente recoge noticias de medios, Steam y Reddit, detecta de qué juego trata cada artículo, agrupa las que cubren el mismo evento y enriquece las supervivientes con IA antes de publicar un sitio estático.

La decisión de diseño que más condiciona el proyecto: **reducir el trabajo antes de la inferencia es más valioso que hacer cada inferencia más rápida**. El límite por juego se aplica dos veces —antes y después de la IA— más un pre-ranking barato con señales sin LLM (recencia, valor noticioso, fuentes verificadas). En una ejecución real eso bajó de 64 historias a 13 llamadas de IA: un 80% menos.

- Interfaz `AIClient` neutral de proveedor: Ollama local (`llama3.2:3b`) con fallback a Groq en la nube.
- Manejo de fallos en dos niveles: salida inválida del modelo se reintenta, fallo de infraestructura cambia de proveedor. Un ítem fallido recibe fallback en vez de matar la ejecución.
- Frontend en HTML, CSS y JavaScript vanilla, sin build step ni dependencias de runtime.
- 303 tests con `pytest` y lint con `ruff`.
